# GAVFS 1.0 — Draft specification

## 1. Scope and terminology

**Provider**: the consumer-facing autonomous ride-hailing service represented by the feed.
**Consumer**: an application using GAVFS to show or plan rides.
**Rider**: the person who may ultimately book a ride.

MUST, SHOULD and MAY express normative requirements. Each feed MUST describe exactly one provider. GAVFS 1.0 covers discovery, service geography, products, pickup estimates, trip estimates and provider-app handoff. It does not specify accounts, dispatch, payment, cancellation or confirmed booking.

## 2. Transport and envelope

Providers MUST publish a publicly discoverable HTTPS `gavfs.json` manifest. All feed URLs MUST use HTTPS. Static JSON resources MUST return a JSON object with `last_updated` (RFC 3339 timestamp) and `data` (object). Dynamic endpoints MUST return a JSON object with `last_updated` and `data`. All coordinates use WGS84 latitude and longitude decimal degrees. Distances are meters, durations are seconds, currencies use ISO 4217 codes, and timestamps use RFC 3339.

Providers SHOULD supply appropriate HTTP cache headers. Consumers SHOULD respect cache headers and rate limits. `gavfs.json` MUST list `provider`, `service_areas`, `products`, `eta`, and `trip_planning` feeds; `service_status` is OPTIONAL.

Example manifest:

```json
{
  "version": "1.0",
  "last_updated": "2026-09-26T08:30:00Z",
  "data": {
    "feeds": [
      {"name": "provider", "url": "https://av.example/gavfs/provider.json"},
      {"name": "service_areas", "url": "https://av.example/gavfs/service_areas.json"},
      {"name": "products", "url": "https://av.example/gavfs/products.json"},
      {"name": "eta", "url": "https://av.example/gavfs/eta"},
      {"name": "trip_planning", "url": "https://av.example/gavfs/trip_planning"}
    ]
  }
}
```

## 3. Access and authentication

Consumers MUST be able to retrieve service information, pickup estimates and trip estimates without authenticating an individual rider. Providers MAY require an application-level API key for quotas, analytics or abuse prevention. Such keys MUST identify consumer applications, not rider identities. Consumer application keys MUST NOT be embedded in publicly distributed client software where confidentiality is expected. Authentication, identity verification and payment during booking remain with the provider.

## 4. provider.json

The `data` object MUST contain `provider_id` (stable string), `name` (display string), `url` (HTTPS), `timezone` (IANA timezone), `language` (BCP 47 language tag) and `booking.deep_link` (provider app URI or universal link). `support.phone`, `support.url`, `booking.web_url`, `booking.app_store_url` and `booking.play_store_url` are OPTIONAL.

The base booking link advertises app-handoff support. Consumers MUST use the fully formed trip-specific booking link from trip planning to hand off a planned ride, rather than constructing one themselves.

## 5. service_areas.json

`data.service_areas` MUST be an array of objects. Each area MUST contain `area_id` (unique within feed), `name`, `geometry` (valid GeoJSON Polygon or MultiPolygon), `pickup_allowed` (boolean), `dropoff_allowed` (boolean), and `has_surge` (boolean). Areas MAY include `product_ids` and `operating_hours` in future revisions; these fields have no normative semantics in this draft.

`has_surge: true` means surge pricing MAY occur for trips originating in the area. `has_surge: false` means the provider does not use surge pricing for trips originating in the area. This field does NOT indicate whether surge is active at the moment. Providers SHOULD define non-overlapping areas or document precedence where areas overlap. Consumers MUST obtain actual trip prices from `trip_planning`.

## 6. products.json

`data.products` MUST be an array. Each product MUST contain `product_id` (unique within feed) and `name`. `description`, `capacity.passengers` (nonnegative integer), `capacity.wheelchairs` (nonnegative integer), `amenities` (array of strings) and `accessibility` (object) are OPTIONAL. Amenities MAY use new string values without changing the specification. Consumers SHOULD gracefully display unknown amenity values.

## 7. ETA endpoint

`GET /eta?lat=<latitude>&lon=<longitude>` returns `data.location` and `data.estimates`. Each estimate MUST contain `product_id` and `pickup_eta_seconds` (nonnegative integer). Product IDs MUST match products in `products.json`. ETA values are nonbinding estimates, not reservations. A successful empty estimates array means no available estimate; it MUST NOT imply a booking was made.

## 8. Trip planning endpoint

`GET /trip_planning?start_lat=<lat>&start_lon=<lon>&end_lat=<lat>&end_lon=<lon>` returns `data.trips`, an array of possible trip options. Optional query parameters MAY include `passengers` and `product_id`.

Each trip MUST contain `product_id`, `pickup_eta_seconds`, `duration_seconds`, `fare`, and `booking.deep_link`. Trips MAY include `trip_id`, `distance_meters`, `pickup`, `dropoff`, and `booking.web_url`. The deep link MUST be fully constructed by the provider and SHOULD prepopulate origin, destination and selected product. A consumer MUST NOT interpret a deep link as a confirmed reservation.

Fare objects MUST contain `currency` and `type`. For `type: "estimated"` or `type: "guaranteed"`, `amount` MUST be provided as a nonnegative number. For `type: "estimated_range"`, `minimum` and `maximum` MUST be provided and minimum MUST NOT exceed maximum. A guaranteed fare SHOULD include `expires_at`. Consumers MUST label estimated fares as estimates and MUST NOT imply that an estimated fare is guaranteed. Estimates SHOULD ordinarily match the provider's booking screen; minor differences MAY occur due to surge pricing, changing conditions, fees or elapsed time.

## 9. service_status.json (optional)

`data.status` MUST be one of `operating`, `limited`, or `suspended`. `data.message` MAY provide rider-facing explanatory text.

## 10. Errors, privacy and evolution

Invalid query parameters SHOULD return HTTP 400 with JSON error information; rate limiting SHOULD use HTTP 429 and a Retry-After header where practical. Consumers SHOULD avoid collecting unnecessary precise location histories. Providers SHOULD avoid returning personally identifying information or rider-specific tokens in public responses.

Future revisions may add formal JSON Schema, provider capability flags, more detailed geographic exceptions, guaranteed quote semantics, and an optional authenticated booking extension. These are outside the normative 1.0 draft.
